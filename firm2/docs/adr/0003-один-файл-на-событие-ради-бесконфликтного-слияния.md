# ADR-0003. Один файл на событие вместо общего журнала

- Статус: принято
- Дата: 2026-09-21
- Контекст: хранилище событий для статистики времени

## Контекст

Событийная модель (ADR-0002) требует хранилища. Оно должно переживать сессии,
коммититься вместе с кодом и читаться генератором дашборда.

Ключевое обстоятельство: маршрут допускает **параллельную разработку до трёх
задач одновременно**, каждая в своём git worktree со своей веткой. Все ветки
вливаются в `feature/<change>`. Значит любой файл, в который одновременно пишут
несколько веток, будет конфликтовать при каждом слиянии.

Рассматривались:

1. Общий append-only журнал `.firm/events.jsonl`.
2. Файл на событие `.firm/events/<iso-ts>-<ticket>-<stage>.json`.
3. SQLite `.firm/firm.db`.

## Решение

**Один файл на событие.** Имя содержит метку времени, тикет и стадию, поэтому
коллизии имён исключены.

## Обоснование

- Append-only журнал конфликтует в хвосте при каждом слиянии параллельных
  веток — а это самый частый случай в новом маршруте, а не редкий.
- SQLite — бинарный файл, git не умеет его сливать вообще; при трёх
  параллельных ветках он будет теряться при каждом мерже.
- Файлы-на-событие не конфликтуют никогда: разные ветки создают разные файлы.
- Читается тривиально и без инструментов; история в git; удаление события
  видно в диффе.
- Конфликт в машинно-сгенерированном файле человек разрешить не может в
  принципе — значит формат обязан исключать конфликт, а не смягчать его.

Тот же аргумент независимо привёл к решению **не коммитить дашборд**: HTML
пересобирается на каждом событии, и коммитимый перегенерируемый файл дал бы
неразрешимый конфликт при каждом слиянии. Дашборд лежит в `.gitignore`.

## Следствия

- Количество файлов растёт линейно по числу переходов. При поставке в
  10 задач это порядка 100–150 мелких файлов на change. Приемлемо; при
  необходимости события архивируются вместе с change.
- Генератор дашборда читает каталог целиком — операция дешёвая, поэтому
  пересборка возможна на каждом событии.
- Дашборд как артефакт нигде не хранится; для просмотра с телефона он
  публикуется отдельной командой.

## Поправка от 2026-10-01: имя файла не было уникальным

В исходной редакции стояло «коллизии имён исключены». Это верно для разных тикетов и
стадий — и неверно для состязательной панели: три ревьюера пишут `review/started` по
одному тикету, и попадание в одну миллисекунду давало ОДИН файл вместо трёх. Молча:
последний вошедший затирал предыдущих, в журнале не оставалось следа, `doctor` ничего не
находил, потому что находить было нечего. Нашли автотесты на инварианты, в первый же день.

Исправлено дописыванием номера к занятому имени (`…-review-started-2.json`). Два следствия
стоит знать:

- запись идёт флагом `wx` (создать или упасть), а не проверкой существования: события
  пишут РАЗНЫЕ процессы, и между «проверил» и «записал» помещается чужая запись. Это
  единственная проверка, которую здесь нельзя обогнать;
- имя файла остаётся идентичностью события (на него ссылается `corrects`), но перестаёт
  быть выводимым из содержимого. Разбирать имя обратно нельзя — и никто этого не делает:
  `listEvents` читает содержимое, а имя использует лишь как ключ и запасной признак
  порядка.
