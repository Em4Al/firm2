# ADR-0002. Переходы статусов пишет код оркестратора, а не hook-и

- Статус: принято
- Дата: 2026-09-21
- Контекст: требование «workflow должен быть детерминированным, а не вероятностным»

## Контекст

Исходное требование звучало как «смена статуса задачи основана на hook»:
разработчик закончил — hook, тестировщик взял — hook, ревью прошло — hook.
Цель — собрать статистику времени по каждой задаче от взятия в работу до мержа.

Проверка окружения дала ограничивающий факт: **множество hook-событий Claude
Code закрытое, в нём 9 элементов** — `PreToolUse`, `PostToolUse`,
`UserPromptSubmit`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`,
`PreCompact`, `Notification`. Произвольные имена событий валидатор отклоняет.
События «разработчик закончил задачу» среди них нет и быть не может.

Единственный способ получить такое событие из hook-а — разобрать транскрипт
завершившегося субагента и догадаться, что именно он сделал. Это вероятностный
детектор, переодетый в hook, то есть ровно то, от чего требование уходило.

При этом детерминированный источник уже существует: оркестрирующий workflow —
это **код**, а не модель. Он сам последовательно вызывает разработчика,
тестировщика и ревьюера и точно знает границы стадий.

## Решение

**События переходов пишет код оркестратора** на границах фаз.

`SubagentStop`-hook оставлен как ремень безопасности, а не как источник: перед
запуском агента оркестратор кладёт в worktree `.firm/current.json` с
`{ticket, stage, attempt}`; hook читает его и проверяет, что парное событие
появилось. Если события нет — hook возвращает `exit 2` и блокирует завершение.
Имя ветки (`task/T-XXX`) служит перекрёстной проверкой тикета.

Событие мержа пишет git-hook `post-merge` — он же обновляет граф кода.

## Обоснование

- Код детерминирован по построению; разбор транскрипта — нет.
- Ремень безопасности превращает дыру в статистике из тихого пропуска в громкую
  ошибку, останавливающую сборку. Незамеченная дыра хуже остановки, потому что
  делает недостоверной всю метрику.
- `post-merge` срабатывает независимо от того, прошёл мерж через движок или был
  сделан руками. Шаг внутри движка можно обойти, git-hook — нет.

## Следствия

- Часть маршрута, идущая вне workflow (человеческие ворота, ручные действия),
  требует отдельных точек записи событий; они перечислены в сводном документе.
- Проектная часть hook-ов (`.firm/hooks/subagent-stop.sh`) получает конкретное
  содержание вместо нынешней заглушки.
- Статус в frontmatter задачи — производный кэш; при расхождении с событийным
  логом побеждает лог.

## Поправка от 2026-09-21 (при реализации)

Статус решения не меняется: переходы пишет **код**, а не разбор поведения модели.
Меняется то, **какой именно код**, потому что при реализации выяснились два факта.

**Факт 1. Workflow-скрипт не может писать файлы.** У скриптов Workflow нет доступа к
файловой системе и Node API (там же запрещены `Date.now()` и `new Date()` — иначе
сломался бы resume). То есть «оркестратор пишет событие» в буквальном виде неисполнимо:
оркестрирующий код — единственное место, где точно известны границы стадий, и ровно оно
лишено права записи.

**Факт 2. Утверждение «множество hook-событий закрытое, в нём 9 элементов» устарело.**
Событий больше тридцати, и среди них есть `SubagentStart` и `SubagentStop`, а в payload
приходят `agent_type`, `agent_id`, `cwd`, `transcript_path` и `last_assistant_message`.

Из второго факта следует, что исходное возражение против хуков снимается. Оно звучало
так: единственный способ получить из хука событие «разработчик закончил» — догадаться по
транскрипту, что агент сделал. Догадываться больше не нужно:

- **стадия** выводится из `agent_type` (`firm-developer` → `dev`, `firm-tester` → `test`,
  `firm-reviewer-qa` → `review`) — отображение, а не вывод;
- **вердикт ревью** берётся из structured output роли (машинный JSON в
  `last_assistant_message`), а не из пересказа;
- **тикет** берётся из маркера `FIRM2-TICKET: T-XXX`, который в промпт кладёт **код**
  workflow-скрипта; хук ищет эту строку точным поиском в машинно-сгенерированном тексте.

### Решение в редакции после проверки окружения

События пишет код, распределённый по трём точкам записи:

1. хуки `SubagentStart` / `SubagentStop` — стадии `dev`, `test`, `review`;
2. git-хук `post-merge` — `merge/finished` и `release/finished`;
3. CLI `firm-event.mjs record` из команд маршрута — границы, до которых не достают
   первые два (ворота человека, отмена задачи, ручные действия).

Хуки запускает рантайм Claude Code: в этой точке у модели нет хода, поэтому «завершился,
но не записал» невозможно — либо субагент завершился и хук отработал, либо не завершился.

### Ремень безопасности — на месте, но перевёрнут

Раньше предполагалось: оркестратор кладёт `.firm/current.json`, а хук проверяет, что
событие появилось. Теперь пишет хук, а проверяется **привязка**: не нашлось ни маркера,
ни `.firm/current/<agent_id>.json`, ни ветки `task/T-XXX` — событие всё равно пишется,
но с `ticket: "unknown"`, и хук возвращает `exit 2`. Смысл тот же: незамеченная дыра в
статистике хуже остановки, потому что делает недостоверной всю метрику. Дыры видны
командой `firm-event.mjs doctor`.

### Проверено зондом 2026-09-21

Главное сомнение — срабатывают ли хуки на субагентах, порождённых Workflow — снято
экспериментом в живой сессии: срабатывают, `agent_type` приходит с префиксом плагина,
`last_assistant_message` приходит.

Там же выяснилась деталь, без которой механизм не работал бы: маркер тикета лежит в
**`agent_transcript_path`** (собственный транскрипт субагента), а не в `transcript_path`
(родительская сессия). Родительский транскрипт для привязки негоден и по размеру, и по
существу: при трёх параллельных задачах в нём лежат маркеры всех трёх.

Запасная линия (`firm-event.mjs claim` из роли) сохранена как вторая ступень привязки,
но основной путь подтверждён.
