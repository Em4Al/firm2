# Обкатка firm2 — чек-лист пилота

Что делать в **отдельном** проекте, чтобы прогнать маршрут по одной сессии за раз.
Замысел и обоснования — `firm2-design.md`; здесь только порядок действий и проверки.

Обкатка поэтапная намеренно: маршрут меняет шесть механизмов сразу, и при первом сбое
иначе будет непонятно, какой из них виноват.

---

## 0. Подготовка

**Один раз на машине** (уже сделано 2026-09-21):

```
/plugin marketplace update firm2
/plugin install firm2@firm2 --scope user
```

Признак успеха — в списке команд появились `/firm-discovery`, `/firm-plan`, `/firm-build`,
`/firm-help`. Своих skills у firm2 нет, в перечне навыков он не появится — это нормально.

**Проект для пилота.** Отдельный: не маркетплейс и не `проект-Д`. По замыслу нужен
гибрид — новый, но с уже лежащим кодом, то есть `firm_initialized: false` и
`has_code: true`. Именно эта комбинация и заставила отказаться от признака «greenfield».

**Размер задачи.** 2–4 задачи. Меньше — параллелизм ни разу не включится и проверять будет
нечего; больше — разбор при сбое перестанет быть обозримым.

Claude Code открывать **в каталоге пилотного проекта**: команды опираются на
`CLAUDE_PROJECT_DIR`, из чужого каталога они будут смотреть не туда.

## 1. Сессия первая — разведка

```
/firm-discovery "<что нужно сделать, своими словами>"
```

Что происходит: preflight окружения (git на `main`, `openspec init`, `.firm/config`,
git-хук `post-merge`), проверка `codegraph`, затем PM ведёт опрос.

Про codegraph вас **спросят** — ставить ли глобально (`npm i -g @optave/codegraph` на пин
из конфига). Глобальный пакет меняет машину целиком, поэтому решение оставлено человеку.
Откажетесь — маршрут пойдёт дальше без графа: sequence-диаграммы Архитектор нарисует с
нуля, а MR-ревью на сборке лишится `diff-impact`. Отказ запишется в
`codegraph.enabled: false`, второй раз не спросят.

**Вопросы опроса задаёт PM**, оркестратор только транслирует — отвечать надо по существу,
раундов будет несколько.

### Проверить до перехода дальше

```bash
grep -E '^engine:|^engine_root:' .firm/config
test -x .git/hooks/post-merge && echo "git-хук на месте"
ls docs/product/ docs/adr/ CONTEXT.md
```

| Что смотрим | Почему это стоп-фактор |
|---|---|
| `engine: firm2` | по этому ключу хук понимает, что события проекта пишет firm2. Нет ключа — **журнал не ведётся вовсе**, и вся статистика окажется пустой |
| `engine_root` | путь к исходнику `firm2`. Указывает в кэш `~/.claude/plugins/cache` — будете отлаживать устаревшую копию |
| `.git/hooks/post-merge` | без него не пишутся события слияния и выпуска, а граф кода не обновляется |
| каталог worktree в `.claude/settings.json` | без него сборка спрашивает подтверждение на каждую правку файла в рабочем дереве задачи. Проверить: `node "$ENGINE/scripts/firm-permissions.mjs"` — скажет «уже согласованы» либо допишет |
| `docs/product/BRD-*.md` | без BRD планировать не из чего: `/firm-plan` остановится сам |

Дальше удобно завести переменную и звать скрипты через неё:

```bash
ENGINE="$(sed -nE 's/^engine_root:[[:space:]]*"?([^"#]+)"?[[:space:]]*$/\1/p' .firm/config)"
echo "$ENGINE"
```

## 2. Сессия вторая — планирование

**Новая сессия** (`/clear` или новое окно) в том же проекте:

```
/firm-plan
```

Архитектор режет задачи файлами `openspec/changes/<change>/tasks/T-XXX.md`, пишет
`design.md`, спеки-дельты и диаграммы в `docs/architecture/`. Есть задачи с `ui: true` —
Дизайнер собирает `docs/design/<change>/ui.html`.

### На воротах смотреть в первую очередь

Два поля frontmatter, от которых зависит весь план сборки:

- **`depends_on`** — по нему планировщик отличает «ждёт зависимости» от «ждёт слот».
  Ошибка здесь вскроется только на прогоне, и выглядеть будет как простой слотов.
- **`parallel_safe`** — можно ли вести задачу одновременно с другими. Здесь стоял совет
  «сомневаетесь — пусть стоит `false`: цена ошибки конфликт слияния, а не потерянный
  час». **Совет снят 05.10.2026 замером.** На проект-В 43 задачи из 72 оказались
  исключительными, и прогон шёл в одну полосу при трёх слотах: 82% рабочего времени одна
  стадия, три слота заняты 11% времени. Цена осторожности — не потерянный час, а
  удвоение календарного срока. Теперь исключительность требует причины (`exclusive_why`),
  и движок называет её при запуске задачи и считает долю в предупреждениях.

Проверка доски:

```bash
node "$ENGINE/scripts/firm-state.mjs" board
```

Замечания на этих воротах — это правки Архитектору и Дизайнеру, а **не баги**: сборка ещё
не начиналась, заводить на них BUG нечего.

---

## 3. Сессия третья — сборка

Снова **новая сессия**:

```
/firm-build
```

Здесь проверяется главное — что журнал переходов ведётся сам.

### Смотреть по ходу

```bash
ls .firm/events/                                    # события должны появляться БЕЗ вашего участия
node "$ENGINE/scripts/firm-event.mjs" doctor --json
node "$ENGINE/scripts/firm-state.mjs" board
open .firm/dashboard.html
```

Признак здоровья: в `doctor` пусто в полях `unknown` и `broken`. Живой ход прогона —
`/workflows`.

### Демо-ворота

Живой запуск, показ сценариев, **явное «ок»** до мержа. Замечание с демо → баг заводится
**всегда** (след остаётся) → триаж Архитектора: `blocker` порождает задачу-исправление
`T-XXXf`, `not_blocker` уезжает в бэклог. Статус исходной задачи назад не откатывается:
она уже `merged`, и откат сломал бы календарную метрику.

## Если надо прерваться

`/firm-pause` — начатые задачи доводятся до конца вместе со слиянием, новые не берутся,
прогон завершается сам. Продолжить в другой сессии: `firm-state.mjs resume`, затем
`/firm-build`. Влитые задачи заново не пойдут — список строится из журнала.

Обрывать прогон на полуслове (`/workflows` → остановка) тоже можно, но тогда останутся
грязные рабочие деревья и недописанные события, и разбирать их придётся руками.

## Если что-то пошло не так

| Симптом | Где искать |
|---|---|
| `.firm/events/` пуст после первой стадии | нет `engine: firm2` в `.firm/config`, либо `engine_root` указывает не на исходник |
| в `doctor` появились `pending_binding` | это не дыра: идущие сейчас стадии, тикет которых станет известен на финише. `ok` при них остаётся `true`, слоты они занимают |
| в `doctor` появились `unknown` | сначала посмотрите, какие именно события. Событие `*-started` **идущей сейчас** стадии без тикета — норма: собственного транскрипта у субагента на старте ещё нет, и привязка достроится по `agent_id`, когда стадия финиширует (`resolved_by_agent_id` в `doctor` показывает, сколько так восстановлено). А вот `finished`/`accepted`/`rejected` без тикета — настоящая дыра: маркеры `FIRM2-TICKET` не доехали до промпта стадии, чинить **до** продолжения |
| хук ругается `exit 2` | то же самое, только громко. Так и задумано |
| worktree заводятся внутри репозитория | `worktrees_dir` должен быть `../<repo>.worktrees`: codegraph индексирует дерево целиком и посчитал бы каждый worktree за копию кода |
| события мержа не пишутся | не установлен `.git/hooks/post-merge` |
| события исчезли целиком | кто-то прибрался в главном дереве. Движок кладёт каждое событие в индекс сразу при записи, поэтому `git clean -fd` их больше не трогает, но в самой поставке журнал всё равно надо коммитить — это делает шаг слияния |
| хук ругается «оставила файлы в ГЛАВНОМ дереве» | ловушка сработала вовремя: стадия записала файл мимо своего worktree. Сверить с версией в дереве задачи и удалить копию из корня — тогда ветка сольётся. Игнорировать нельзя: слияние упадёт позже, когда разбирать дороже |
| слияние падает на «untracked working tree files would be overwritten» | стадия записала файл по относительному пути, и он лёг в главное дерево вместо worktree. Промпт стадий теперь требует абсолютных путей и самопроверки `git status` в корне; шаг слияния сверяет дубль с веткой и удаляет только полностью совпадающий |
| тестировщик просит подтвердить правку кода с откатом `git checkout --` | это мутационная проверка. Приём законный, но смотрите на путь: относительный означает ГЛАВНОЕ дерево, где лежит работа других задач, и откат выбросит её вместе с мутацией. Отвечать **нет**; промпт стадии теперь требует делать это только внутри worktree по абсолютным путям |
| `unable to unlink old '.idea/….iml'` посреди слияния | каталог IDE под версией: его правит работающая IDE, а git трогает на каждом переключении веток. Разрешением не лечится — развязать: `git rm -r --cached .idea && echo ".idea/" >> .gitignore`. `firm-permissions.mjs` предупреждает об этом при запуске |
| `git worktree list` показывает `prunable` | каталог снесён, а служебная запись в `.git/worktrees` осталась. Удаление дерева — две команды: `worktree remove`, затем `worktree prune`. Шаг слияния делает обе, стадия `leftovers` подчищает в конце прогона; вручную — `firm-state.mjs prune` |
| после сборки висит сервер или браузер | шаг слияния гасит процессы задачи по пути её рабочего дерева, а в конце прогона стадия `leftovers` перечисляет всё, что осталось. Вслепую движок не убивает: по тем же шаблонам ходят ваши собственные процессы |
| проект на Django (или любой с секретом в коде) | `django-admin startproject` кладёт `SECRET_KEY` литералом в `settings.py` — так стартует **каждый** проект на Django, и каждый упрётся в защиту учётных данных, как только файл понадобится стадии. `firm-permissions.mjs` предупреждает об этом на разведке. Вынести секрет в `.env` заранее дешевле, чем разбираться посреди сборки |
| задача застряла «в слиянии», `doctor` отвечает `ok` | так выглядел отказ мержа до 0.2.2: событие не писал никто. Теперь стадия пишет `merge/failed`, `doctor` показывает `failed_merges` и снимает `ok` |
| `release` вернул `released: 0` на закрытой поставке | спека уехала в `changes/archive/<дата>-<change>` раньше мержа в main. С 0.2.2 задачи ищутся и там; на старом движке — перезапустить `firm-event.mjs release --change <имя>` после обновления |
| стадия правит общие конфиги и зависимости | промпт это запрещает с 0.2.2: общее хозяйство меняется только по критерию приёмки своей задачи. Уже попавшее — откатывать отдельным коммитом, а не молча |
| правка команды или роли не доехала до проекта | `marketplace update` сверяет версию в манифесте и при прежней версии считает, что обновлять нечего. Поднять версию (`bump-version.mjs`) и обновить снова; уже застрявший кэш лечится `uninstall` + `install`. Подхватится в новой сессии, не в текущей |
| в коммите стадии сотни файлов, а правок — четыре | артефакт прогона остался в рабочем дереве, и роль закоммитила его вместе с работой. До 0.4.74 хук сам предписывал `git add -A`; теперь он перечисляет файлы поимённо, узнанный мусор называет отдельно и на свалке из неизвестных файлов готовой команды не даёт вовсе. Уже уехавшее — отдельным коммитом `git rm -r --cached`, плюс строки из `templates/gitignore.example` |
| браузерных проверок много, и каждая пишет свой стенд | это долг проекта, движок его не закроет: стенд знает про стек и экраны. Промпт стадии велит искать готовый модуль и, если его нет, выносить обвязку в общий — чтобы следующая задача взяла готовое. Цена независимых копий: на проект-В 30 проверок, 12 010 строк и профиль браузера, положенный в репозиторий |
| `doctor` или `build-args` говорят про версию движка | записанная в `.firm/config` разошлась с фактической. Само по себе не ошибка, но `/firm-adopt` ставит ещё и git-хуки движка в `.git/hooks` (`post-merge` и, с 0.4.126, `pre-commit`) — их не доставляет ни `/plugin update`, ни подъём версии, и второго в проектах до первого `adopt` нет вовсе. Звать `/firm-adopt` **между** прогонами: он меняет хук слияния, и делать это под идущим слиянием нельзя |
| задача долго висит на `dev`, хотя код несложный | скорее всего в ней живая проверка в браузере. Поставь `требует-браузера` в `labels` — стадия получит готовый протокол (CDP, `--use-angle=swiftshader`, `textContent` вместо кадра) и пойдёт раньше равных |
| стадия в рабочем дереве падает на сборе тестов: нет секрета | `.env` не под версией, значит в `git worktree` его нет и движок его туда не положит (под песочницей он нечитаем). Чинится на стороне проекта: умолчания в `conftest.py`. `build-args` предупреждает об этом заранее |
| `doctor` показывает `unknown` после MR-ревью | в промпт Ревьюера на шаге 4 `firm-build.md` не положили `FIRM2-TICKET: MR`. Уже записанное чинится `firm-event.mjs claim --ticket MR --stage review --agent-id <id>` |
| в продуктовом коде появился комментарий про песочницу или worktree | стадия объяснила ограничение своей среды в чужом репозитории. Переформулируй продуктовой причиной. Промпт стадий это запрещает начиная с 22.09.2026 |
| `.claude/settings.json` попал в ветку | в нём абсолютные пути этой машины, у коллеги он не сработает: `git rm --cached .claude/settings.json` и строку в `.gitignore`. `firm-permissions.mjs` предупреждает, если файл под версией |
| стадии отказано в записи в файл с секретами (`settings.py`, ключи) | это защита учётных данных. Порядок такой: **сначала вынести секреты** из файла в `.env` (он остаётся закрытым, и правильно), **потом** разрешить каталог в `allowWrite`. Обратный порядок — расширение прав поверх секрета в коде — снимает защиту ровно там, где она нужна. Защита держится на именах вроде `SECRET_KEY`, а не только на значениях: файл остаётся закрытым и после выноса литерала, и закрыт весь каталог целиком (новый файл создать нельзя, старый удалить нельзя) |
| `.env` нечитаем под песочницей | так и задумано: это учётные данные. Значит загрузчик (`load_dotenv` и подобные) обязан переживать отказ чтения, а не падать: оберните вызов в `try/except OSError`. Иначе тесты под песочницей не запускаются даже тогда, когда переменные уже переданы в окружении |
| роль просит поставить инструмент (`npx --yes`, `npm i -g`, `pip install`) | отвечать **нет**: пакет меняет машину целиком и выбирает версию за вас. Промпт стадий это запрещает, а нехватку инструмента велит описать в `notes` — решать вам, как в случае с codegraph на разведке |
| роль просит запустить команду без песочницы | обычно это кэш инструмента в `$HOME` (`uv`, `npm`, `cargo`), а не что-то опасное. `firm-permissions.mjs` добавляет кэш того инструмента, которым проект реально пользуется — после этого тесты идут в песочнице и запрос не возникает |
| работа стадии не доехала до поставки | слияние берёт только закоммиченное. Шаг слияния обязан сначала закоммитить хвост в рабочем дереве задачи и лишь потом сливать; `git worktree remove --force` на грязном дереве запрещён прямо в промпте |
| баг закрыт по делу, а в файле `status: open` | закрывает не роль, а факт слияния задачи-исправления: `firm-event.mjs sync` проставит `fixed` и `fix_task`. Нет задачи-исправления или она не влита — баг и должен оставаться открытым |
| галочки критериев приёмки не проставлены | их ставит `sync` по разбору ревьюера, сохранённому в событии. Пусто при принятой задаче — значит ревьюер вернул вердикт без `criteria_results`, и это к нему вопрос, а не к учёту |
| статусы задач разошлись с журналом | норма: `firm-event.mjs sync` пересчитает кэш, авторитетен журнал |
| задачи стоят, слоты пустые | смотреть `depends_on`: зависимость указывает на задачу, которой нет или которая не будет выполнена. В логе Workflow это «Тупик планировщика» |
| роль ушла не на той модели | `firm-state.mjs models` покажет разобранную секцию и предупреждения об опечатках |
| сборка сыплет запросами на разрешение | песочница не знает про `../<repo>.worktrees`: `firm-permissions.mjs` добавит его в `additionalDirectories` и `allowWrite`. Каталог **вне** репозитория намеренно (`firm2-design.md` §9), переносить его внутрь нельзя |
| движок не пишет в `.firm/` | `./.firm` попал в `sandbox.filesystem.denyWrite` — так бывает, когда настройки копируют из репозитория, где firm2 разрабатывают. `firm-permissions.mjs` уберёт |

## Что известно заранее

**Проверено локально:** вывод статусов из журнала, различие `todo`/`ready`, тайминг,
дашборд, три пути привязки события и `exit 2` при их отсутствии, git-хук `post-merge` на
слиянии задачи и поставки, уборка осиротевших worktree, планировщик на моках, оверрайды
моделей.

**Проверено зондом в живой сессии:** хуки срабатывают на субагентах из Workflow,
`agent_type` приходит с префиксом плагина, вердикт читается из structured output,
маркер берётся из `agent_transcript_path`.

**Не проверено и вскроется на пилоте:** поведение `codegraph` под нагрузкой (на Python
числа транзитивных вызывающих занижены — сигнал, но не критерий приёмки), весь маршрут
от начала до конца.

**Откат.** С 0.3.0 `agent-dev-firm` удалён, роли переехали в `firm2` — отката на старый
маршрут больше нет, он только через git (коммит `d2f8912` и раньше).

## Что решено отложить до конца обкатки

**Браузерная проверка экранов.** На T-009 стадия сама собрала себе браузер: сняла
скриншот headless-Chrome, потом подняла его с портом удалённой отладки. Установить

стадии: без гашения процесса, со случайным портом, заново на каждой задаче.

Заводить это надо один раз и осознанно — решить, нужна ли машинная проверка UI в
проекте вообще, каким инструментом, кто его ставит и как он убирается за собой. Пока
решения нет, экраны смотрит человек на демо-воротах: это их прямое назначение, и
отсутствие машинной проверки не делает задачу непринятой.

## Дефекты движка с прогона проект-Б (23.09.2026)

Все вскрылись за один мерж — слияние T-105. Первые три закрыты в 0.3.1, четвёртый — в
0.4.0; все проверены на синтетическом репозитории.

### Д-1. Статус-кэш патчится в главном дереве, пока задача не влита — ЗАКРЫТ в 0.3.1

`firm-event.mjs sync` правит `status:` в `openspec/changes/<change>/tasks/T-XXX.md`
главного дерева. Ту же строку правит сама задача у себя в worktree — она отмечает
выполненные критерии и дописывает протокол. Слияние встаёт с «Your local changes to
the following files would be overwritten by merge», и так будет на **каждой** задаче:
до T-105 не всплывало только потому, что стадии успевали закоммитить раньше.

Лечится порядком, а не правами: файл задачи в главном дереве не трогать, пока задача
не влита, а `sync` гонять после мержа. Статус — производный кэш (ADR-0001), выбросить
его ничего не стоит: на разборе так и сделали — `git stash` двух файлов, мерж,
`sync` поверх влитого.

**Закрыто:** `syncStatuses` пропускает задачи, чья ветка `task/T-XXX` ещё не влита
(`inFlightTickets` в `lib/firm.mjs`), и сообщает их в поле `deferred`. `post-merge`
зовёт `sync` сразу после слияния, так что кэш догоняет журнал тогда же.

### Д-2. Шаг слияния не узнаёт отказ песочницы — ЗАКРЫТ в 0.3.1

Промпт `mergeTicket` разбирает только `untracked working tree files would be
overwritten`. На `Operation not permitted` (песочница закрыла каталог — на пилоте это
был `config/` проекта Django) роль начинает изобретать обходы: удалять файлы,
коммитить промежуточное, просить снять песочницу целиком. Событие `merge/failed` она
при этом записывает верно, но причина в `notes` тонет среди выдумок.

Надо: отдельная ветка в промпте — отказ вида `Operation not permitted` / `unable to
unlink` не чинится из git вовсе; записать `merge/failed`, назвать закрытый путь и
сказать человеку, что это `/sandbox`, а не рабочее дерево.

**Закрыто:** отдельная ветка в промпте `mergeTicket` — «из git это не чинится ничем,
не выдумывай обходов», `status: fail` с точным закрытым путём.

### Д-3. «local changes would be overwritten» в промпте нет вовсе — ЗАКРЫТ в 0.3.1

Родственник Д-1, но шире: на разборе он прилетел дважды подряд и от разных причин —
сперва от неза­коммиченного события журнала, потом от файлов задач. Лечение одинаковое
(закоммитить или отложить), а в промпте шага слияния этого случая нет.

**Закрыто, и глубже, чем формулировкой.** Причина воспроизведена на синтетическом
репозитории: `writeEvent` кладёт новое событие сразу в индекс (иначе `git clean` его
сносит), а `git merge` отказывается работать при неподготовленном индексе — даже когда
спорный файл отсутствует в обеих сливаемых ветках. Коммит журнала переехал из шага
после слияния в шаг ДО него; разбор «что именно мешает» в промпте тоже появился.

### Д-4. Запрет писать в главное дерево держится на тексте — ЗАКРЫТ в 0.4.0

Тестировщик T-105 записал оба своих теста по относительному пути, и они ушли в главное
дерево вместо worktree задачи. Промпт это запрещает (`firm2-build.js:182`), но запрет
чисто словесный: относительный путь пишется по невнимательности, а словами такое не
ловится.

**Закрыто:** хук `PreToolUse` на `Write|Edit` → `hooks/write-guard.sh` →
`scripts/write-guard.mjs`. Событие именно `PreToolUse`, а не `PostToolUse`: после записи
файл уже в главном дереве и слияние уже сорвано, остаётся только сообщить. Код 2
отменяет сам вызов.

Правило: пока живо хотя бы одно рабочее дерево задачи, запись по пути внутри главного
дерева отклоняется — кроме `.firm/`, `openspec/`, `docs/`, `.claude/`, которые
принадлежат поставке, а не задаче. Признак «идёт сборка» взят по живому worktree, а не
по роли агента: роль в полезной нагрузке `PreToolUse` не гарантирована, а деревьев до
сборки нет и после уборки не остаётся.

Аварийный выход — `guard: write_outside_worktree: off` в `.firm/config`.

Проверено двенадцатью сценариями на синтетическом репозитории: блокируются
относительный путь и файл в корне; проходят запись в worktree задачи, `openspec/`,
`docs/`, `.firm/`, путь вне репозитория, состояние после уборки деревьев, `guard: off`
и чужой движок.

Проверка нашла в самой защите два дефекта, ни один не был виден по коду. На macOS
`/tmp` — симлинк на `/private/tmp`: пути не сходились, защита молчала (лечится
приведением к реальным путям). И `git worktree list` показывает деревья, помеченные
`prunable` — каталог снесён, а `worktree prune` не позван: для защиты это ложное «идёт
сборка», запись в главное дерево была бы запрещена навсегда. Живым считается только
существующий каталог. Второй дефект нашёлся на реальном проекте — в проект-Б
после слияния висел prunable `T-102`.

### Д-5. Согласование песочницы советовало, но не проверяло — ЗАКРЫТ в 0.4.1

`firm-permissions.mjs` раскладывал границы и печатал советы («вынеси секрет, потом
разрешай каталог»), но ни разу не проверял, может ли он на самом деле писать туда, куда
собирается. На пилоте `config/` оказался закрыт, скрипт промолчал, и отказ вылез на
слиянии T-105 — посреди сборки, где он стоит человеческого разбора.

**Закрыто:** после правки настроек (и отдельно по `--probe-only`) скрипт создаёт и
удаляет файл в каждом каталоге поставки — корень, `.firm`, каталог рабочих деревьев,
все каталоги верхнего уровня под версией.

Код ошибки называется вслух, потому что он и есть диагноз: `EPERM` — песочница
(правами не перебивается, только `/sandbox`), `EACCES` — права ФС, `EROFS` — том
только на чтение. Различие установлено на самом пилоте: `tests/` и `config/` с
одинаковым `mode=0755`, одним владельцем и одним euid — первый писался, второй отдавал
`EPERM`. До этого две догадки (права ФС; литерал секрета в `settings.py`) оказались мимо,
и обе стоили времени — именно поэтому проба печатает код, а не пересказ.

### Д-6 — спека архивировалась до приёмки поставки — ЗАКРЫТ (0.4.6)

Workflow звал Технического писателя сразу, как только все задачи приняты **поштучно**
(`allAccepted`). Но поштучная приёмка — не приёмка поставки: за ней идут MR-ревью всего

Как это выглядело на пилоте 23.09.2026, по журналу и git:

21:30:20  архив спеки + вливание дельт в живые спеки openspec/specs/
21:31:11  MR-ревью началось
21:39:27  MR-ревью: request-changes (три блокера), мерж заблокирован

Поставка оказалась одновременно заархивированной и непринятой. Хуже того, живой каталог

лог, что приёмка поставки ещё впереди.

### Д-8 — адъюдикация невидима в журнале — ЗАКРЫТ (0.4.10)

Стадия `adjudicate` (панель QA разошлась → Архитектор заводит баг и выносит вердикт)
запускается как `firm2:firm-architect`, а этой роли нет в `STAGE_BY_AGENT`. Хук выходит
с нулём и молчит. Следствия шире, чем кажется: стадия невидима для `/firm-monitor` и
`doctor`, а её время попадает в «ожидание» тайминга — то есть в метрику ожидания
человека, которая по замыслу диагностическая. На прогоне 24.09.2026 это дало 34 минуты
тишины в журнале на самой долгой стадии цикла.

**Правка (в исходник НЕ внесена — см. ниже почему).** В `scripts/firm-event.mjs`:

1. в `STAGE_BY_AGENT` добавить три строки:
   `'firm2:firm-architect': 'adjudicate'`, `'agent-dev-firm:firm-architect': 'adjudicate'`,
   `'firm-architect': 'adjudicate'`;
2. сразу после вычисления `ticket`, перед `let kind = ...`:
   `if (stage === 'adjudicate' && ticket === 'unknown') process.exit(0)`.

Второе обязательно: Архитектор работает не только в адъюдикации, он же режет задачи на
`/firm-plan`, где маркера тикета в промпте нет по устройству. Без проверки каждое
планирование засыпало бы журнал событиями `ticket: unknown`, и `doctor` показывал бы их
как дыры. Признак адъюдикации — именно маркер: его кладёт workflow, и только он.

Остальное менять не надо, и это проверено, а не предположено: `statusFromEvents` имеет
`default: break`, поэтому новая стадия статус задачи не трогает; `computeBoard` считает
слоты только по `dev/started`, поэтому счётчик не раздувается; `STAGES` вне `lib/firm.mjs`
нигде не используется.

**Проверено на синтетическом проекте:** Архитектор без маркера — журнал молчит (0
событий); с маркером — пишется `T-201-adjudicate-started`, парное `finished` сходится;
доска показывает `ready` и `слотов 0/3`, `doctor` зелёный.

**Внесено** после закрытия поставки 24.09.2026 — до того держали в стороне намеренно:
`scripts/` читается из исходника, и правка журнала посреди сборки задела бы идущий прогон.

### Д-9 — шаг демо не объясняет, как поднять приложение при закрытом `.env` — ЗАКРЫТ ЧАСТИЧНО (0.4.13)

На демо-воротах 24.09.2026 роль не смогла поднять сервер: `.env` закрыт песочницей на
чтение (`sandbox.credentials.files`, `mode: deny` — защита, которую ставит сам движок),
Django упал на `DJANGO_SECRET_KEY`. Вывод роли: «перезапускаю без песочницы», и следом
совет смотреть `/sandbox` — команды, которой в сборке CLI нет. Оба раза роль пришла к
снятию защиты, потому что инструкция молчит.

Приложению нужен не файл, а переменные окружения, и на демо их можно выдать одноразовыми:

```bash
DJANGO_SECRET_KEY=$(python3 -c 'import secrets;print(secrets.token_urlsafe(50))') \
INTERACTIVE_JWT_SECRET=$(python3 -c 'import secrets;print(secrets.token_urlsafe(32))') \
uv run python manage.py runserver 8000
```

**Сделано в 0.4.13.** В `firm-build.md` §5 появился раздел «если приложение не
поднимается из-за закрытых секретов» с тем же порядком, что и на разведке: сначала
одноразовые переменные окружения, потом обычный Терминал человека, и прямой запрет на
«перезапускаюсь без песочницы» и на совет `/sandbox`. Главная половина дефекта закрыта
именно этим: роль пришла к снятию защиты дважды подряд не потому, что команда неверна, а
потому что инструкция молчала вовсе.

**Что остаётся открытым.** Сама команда так и НЕ проверена на живом проекте — она
записана в `firm-build.md` §5 как пример с явной пометкой об этом, и роли велено сказать вслух, получилось
или нет. Ответ придёт с ближайшего демо на Play; не получится — заменить пример честным
выводом «при закрытых секретах демо поднимает человек в обычном Терминале».

**Поправка 22.10.2026: прежнее сомнение в диагнозе было ошибкой, и ошибкой в чтении
файла.** Здесь было написано, что в `myapp/settings.py:40-48` вызов `load_dotenv`
обёрнут в `try/except OSError`, а значит закрытый `.env` ронять ничего не должен. Обёртка
есть, но в ДРУГОМ проекте — `проект-Б`; пилот шёл в `myapp`, где вызов голый
(`settings.py:29`). Замер вместо рассуждения: `load_dotenv` на файле с правами `000`
бросает `PermissionError [Errno 13]` — `isfile` проходит, `open` падает, и не ловит это
никто. То есть диагноз с пилота был верен.

**И отсюда вторая половина дефекта, которой здесь не было.** Рецепт §5 `firm-build.md` — «выдай секреты
переменными окружения» — в проекте такой формы помочь НЕ МОЖЕТ: падение происходит на
чтении файла, до того как кто-то смотрит на ключи. Поэтому в 0.4.97 §5 `firm-build.md` начинается с
различения двух падений по трейсбеку: «не пришло значение» (пункт 1 годится) и «не читается
сам файл» (пункт 1 пропускается, лечит правка проекта или человек в Терминале). Держит это
рубеж, шаг 3ф.

Там же поправлен устаревший довод: запрет советовать `/sandbox` обосновывался тем, что
такой команды «может не быть вовсе в сборке CLI». В нынешней сборке она есть. Запрет
остался — но по настоящей причине: защиту включал человек, и снимать её ради демо не
решение роли (ADR-0009).

### Д-10 — доска показывает идущую задачу как `ready` — ЗАКРЫТ (0.4.12), зонд встроен

Тикет привязывается к событию на ФИНИШЕ стадии: маркер `FIRM2-TICKET` хук читает из
`agent_transcript_path`, а на `SubagentStart` транскрипта ещё нет. Поэтому в журнале
лежит `unknown-dev-started`, `resolveTickets` подтянет его только парным `stop`, и всё
это время доска показывает работающую задачу как `ready` — то есть «ждёт слот», хотя
слот она уже занимает. Наблюдено на T-106f2 (прогон 24.09.2026): счётчик честный
(`слотов 1/3`), надпись у задачи — нет.

Три возможных ответа, в порядке предпочтения:

1. **Стадия заявляет себя.** В движке уже есть команда `claim`, которая пишет
   `.firm/current/<agent_id>.json`, и хук её читает третьим приоритетом. Её просто никто
   не зовёт. Если добавить вызов первой строкой в промпт каждой стадии, привязка станет
   точной с самого старта. **Требует зонда:** `cmdClaim` берёт идентификатор из
   `CLAUDE_AGENT_ID`, и совпадает ли эта переменная с `agent_id` из полезной нагрузки
   хука — не проверено. Без совпадения приём не работает.
2. **Доска перестаёт врать.** Дешёвый и честный вариант: не писать `ready` у задач, пока
   есть непривязанные идущие старты, а показать их числом отдельной строкой. Имени
   задачи это не даёт, но снимает ложное «ждёт слот».
3. **Привязка по рабочему дереву.** Дерево `T-XXX` создаётся до старта Разработчика, то
   есть имя известно файловой системе. Но при параллельных задачах соответствие
   «непривязанный старт → дерево» неоднозначно, поэтому вариант слабее первых двух.

Начинать с зонда по пункту 1: если `CLAUDE_AGENT_ID` совпадает, остальное не нужно.
**Зонд перестал быть предусловием (0.4.12).** Ставить отдельный опыт с живым субагентом,
чтобы потом реализовать приём, — лишний круг: приём реализован так, что сам же и есть
зонд. Если идентификатора нет, `claim` отвечает `ok: false` с причиной и последствием, и
поведение возвращается к сегодняшнему — привязка остаётся отложенной. Регрессии в этом
случае нет, а ответ на вопрос «совпадает ли `CLAUDE_AGENT_ID`» приходит первым же
прогоном, из журнала, а не из отдельного опыта.

**Сделано в 0.4.12 (основное).** Вариант 1 доведён до конца. `claimLine()` в
`firm2-build.js` кладёт вызов `firm-event.mjs claim` первой строкой в промпт **каждой**
стадии — Разработчика, Тестировщика, Ревьюера-QA и адъюдикации, — и там же сказано, что
`ok: false` это не ошибка роли и не повод останавливаться. `cmdClaim` перестал писать
бесполезный `unknown.json`: без идентификатора он честно отказывается и называет
последствие. Проверено на синтетическом репозитории: с `CLAUDE_AGENT_ID` старт стадии без
маркера лёг файлом `…-T-501-dev-started.json`, доска показала `in_progress` сразу.
Стадийность важна отдельно от старта задачи: по наблюдению ниже каждый переход между
стадиями давал `unknown`, и одной претензии на старте задачи не хватило бы.

**Сделано в 0.4.11 (частично).** `doctor` отделяет оборванные старты от идущих: старт без
парного финиша старше шести часов уходит в `abandoned_starts` с возрастом, а не висит в
`pending_binding` наравне с работающей стадией. Порог щедрый нарочно — стадия Разработчика
на Opus идёт десятки минут, и объявить её оборванной рано хуже, чем показать лишний час.
Чистить журнал при этом не надо и нельзя: запись правдива (стадия началась и не кончилась),
а `ok` от неё не зависит.

**Наблюдение со следующего шага цикла (24.09.2026, T-107f4).** Разработчик закончил в
09:57, через 22 секунды стартовал Тестировщик, его событие легло как
`unknown-test-started`. Доска держит задачу в `in_progress` — и это честно: она
показывает не «работает Разработчик», а «последнее, что я знаю достоверно, — его финиш».
То есть Д-10 задевает не только старт задачи, но и каждый переход между стадиями.

**Поправка к разбору роли, ведущей прогон.** `in_flight_unbound: 0` при непривязанном
событии в журнале — это НЕ признак того, что стадия уже сопоставилась по `agent_id`.
Сопоставиться она не могла: `resolveTickets` берёт тикет из ПАРНОГО события того же
агента, а у идущей стадии парного `finished` ещё нет. Причина в другом: счётчик считает
только непривязанные старты Разработчика (`e.stage !== 'dev'` → пропуск). Это правка
0.2.5, снявшая «слотов 6/3»: задача уже посчитана по своему статусу, и её незакрытые
агенты дали бы второй счёт той же задачи. `doctor` в `pending_binding` считает все
непривязанные события — отсюда расхождение чисел, и оно устроено нарочно.

**Что из замечания верно и должно войти в правку.** Имя файла события пишется один раз, в
момент записи, и остаётся `…-unknown-…` навсегда; `resolveTickets` связывает событие с
тикетом только в памяти, при чтении. Каталог `.firm/events/` поэтому выглядит хуже, чем
состояние на самом деле, и человек, читающий его напрямую, видит дыры там, где их нет.
Это ещё один довод за вариант 1 (`claim`): при привязке на старте имя файла будет верным
сразу, и расхождение «имя против привязки» исчезнет, а не будет залечиваться при чтении.
Переименовывать уже записанные файлы задним числом не надо — журнал иммутабелен (ADR-0003).

### Д-11 — счётчик попыток живёт внутри прогона — ЗАКРЫТ (0.4.11)

`firm2-build.js` начинает каждую задачу с `let attempt = 0`, а `build-args` номер попытки
не передаёт. Значит при перезапуске сборки задача получает промпт попытки 1, и лимит
`MAX_ATTEMPTS = 3` до неё не доходит **никогда**: три попытки в одном прогоне,
три в следующем, и так без предела.

Хуже того, эскалированная панелью задача возвращается в цикл как свежая. Разработчик
видит непустую ветку, готовые критерии и зелёные тесты — и заключает, что работа сделана.
Эскалация, которая по замыслу идёт человеку через арбитраж (`firm-build.md` §3),
растворяется. Обходится только сменой id задачи, то есть вручную.

Наблюдено на прогоне 24.09.2026; там же выяснилось, что и вывод по T-107f2 был неполон:
перезапуск прогнал её попытку 1 заново, а спасло лишь то, что вторая попытка успела
состояться внутри того же прогона.

**Правка (в исходник НЕ внесена):**

1. `firm-state.mjs`, `buildArgs()` — класть в каждую задачу `attempt: t.attempt` и
   `status: t.status`. Поле уже есть: `computeBoard` берёт его из `statusFromEvents`,
   который считает попытки по событиям `dev/started`. Журнал знает ответ, его просто
   не спрашивают.
2. `firm2-build.js`, `buildTicket()` — начинать с `let attempt = task.attempt || 0`,
   чтобы лимит считался по всей жизни задачи, а не по жизни прогона.
3. Эскалированные (`status: blocked`) — добавить в `skip` рядом с `merged`/`released`/
   `cancelled`, чтобы они попадали в `skipped` и доходили до арбитража на уровне команды,
   а не молча перезапускались.

Третий пункт — единственный с решением, а не механикой: он означает, что задача без
человека дальше не пойдёт. Это и есть замысел эскалации, но проверить на прогоне стоит.

**Поправка от роли, ведущей прогон (принята): одного номера попытки мало.** Он чинит
учёт, но не поведение. Разработчик в прошлом прогоне не сделал работу не потому, что
считал её попыткой 1, а потому что промпт не нёс, ЗА ЧТО отклонили. Получив рамку
«попытка 2» и ту же непустую ветку с зелёными тестами, он с той же вероятностью решит,
что работа сделана, — просто в запасе останется одна попытка вместо трёх.

Проверка по коду подтверждает обе половины. Внутри прогона вердикт передаётся: в промпт
идёт строка «Замечания прошлого ревью» из `last.notes`. На перезапуске `last = null`, и
там прочерк. При этом журнал претензию хранит: событие `review/rejected` несёт `notes` и
`criteria` — разбор по критериям приёмки, который кладёт хук из structured output роли.

Поэтому пункт 1 правки расширяется: `buildArgs()` кладёт в задачу не только `attempt` и
`status`, но и `last_verdict` — `notes` и `criteria` последнего `rejected`/`escalated`
события, — а `buildTicket()` подставляет их в промпт вместо прочерка. Тогда «готовую
работу» в дереве Разработчик обязан перечитать против конкретных претензий, а не против
собственного впечатления.

Связка с Д-8: после того как адъюдикация начнёт писаться в журнал, её вердикт и путь к
баг-файлу попадут туда же и станут доступны тем же способом. Сейчас они не переживают
прогон вовсе.

**Дописано 04.10.2026 (0.4.51).** Правка была сделана, а `last_verdict` всё равно
оставался пустым — и причина оказалась не здесь. Вердикт не доезжал до журнала ВООБЩЕ:
на четыре пилотных проекта 328 событий `review/finished` и ровно одно `review/accepted`,
от 22.09.2026, то есть со времён прежнего движка. Хук читал `last_assistant_message`, а
structured output роли приходит не текстом — рантайм кладёт его отдельным блоком
`tool_use` в собственном транскрипте стадии. Поле не пустое и не сломанное, просто
отвечает не на тот вопрос, поэтому молчание выглядело как «ревью ничего не сказало».
Теперь вердикт читается из хвоста транскрипта, а предсказанная выше связка с Д-8
исполнена буквально: адъюдикация пишет `adjudicate/rejected` (blocker) или
`adjudicate/accepted` (not_blocker) с путём к баг-файлу в `notes`.

Урок общий, а не про это поле: **молчание источника надо проверять счётом, а не
чтением кода**. Разбор по коду в своё время подтвердил «обе половины» и был прав в
каждой строке — ошибка была в том, что никто не спросил журнал, сколько в нём вердиктов.
Один запрос `grep` закрыл бы вопрос за десять дней до того, как его закрыл человек,
вписывая вердикт в задачу руками.

### Д-12 — решения человека о судьбе задачи не имеют представления в журнале — ЗАКРЫТ (0.4.11)

Архитектор заменил T-106f2 двумя задачами и проставил ей `superseded_by: [T-112, T-113]`.
`build-args` выдал её на вход **третий раз** — пришлось исключать руками.

Причина глубже списка `skip`, и это видно в коде. `computeBoard` берёт статус **только
из событий**; frontmatter используется, лишь когда событий у задачи нет вовсе (тогда
статус выводится из зависимостей: `todo` или `ready`). У T-106f2 события есть, поэтому:

- `superseded` доска не видит в принципе — для неё задача в работе;
- `cache_stale` для такой задачи истинно, и ближайший `firm-event.mjs sync` **затрёт**
  `superseded` обратно на статус из журнала. Решение человека пропадёт молча.

То же относится к `cancelled`: в `skip` он есть, но задаче, у которой уже были события,
это не поможет.

Корень — в словаре: `STAGES = ['dev','test','review','merge','release']`,
`EVENT_KINDS = ['started','finished','accepted','rejected','escalated','failed']`.
Решения о судьбе задачи (заменена, отменена) там места не имеют, а по ADR-0001 истина —
журнал. Значит решение, которое в журнал не попало, для движка не существует.

**Правка (в исходник НЕ внесена):**

1. `lib/firm.mjs` — добавить стадию `lifecycle` и виды события `superseded`, `cancelled`;
   в `statusFromEvents` — `lifecycle/superseded → 'superseded'`,
   `lifecycle/cancelled → 'cancelled'`. Оба терминальные: идут последними по времени и
   поэтому побеждают.
2. `firm-state.mjs`, `buildArgs()` — в `skip` добавить `superseded` (и `blocked`, см. Д-11).
3. Роль, которая заменяет задачу, обязана записать событие, а не только frontmatter:
   `firm-event.mjs record --ticket T-XXX --stage lifecycle --event superseded`.
   Инструкцию дописать в `firm-plan.md` (там же, где вводится `superseded_by`) и в
   промпт адъюдикации, если замена решается там.

4. **Баги, привязанные к заменённой задаче, повисают.** Баг связан с задачами двумя
   полями frontmatter: `tickets` (в каких задачах наблюдался) и `fix_task` (какая
   задача его чинит). Когда задача уходит в `superseded`, обе ссылки указывают в
   никуда: `fix_task` — на задачу, которая уже не будет выполнена, `tickets` — на
   задачу, которой в поставке фактически нет. Баг при этом остаётся `open`, и выходит
   баг без исполнителя при живых задачах-заменах.

   Автоматически это не решается: какая из заменяющих задач чинит какой баг — решение
   Архитектора, а не вывод из данных. Поэтому делим так:

   - **движок находит** — в `firm-event.mjs doctor` добавить проверку `bugs_on_superseded`:
     баги, чьи `fix_task` или `tickets` указывают на задачу в терминальном статусе
     (`superseded`, `cancelled`). Пустой список входит в `ok`, непустой — нет;
   - **роль перевязывает** — Архитектор, решая заменить задачу, обязан тем же ходом
     перенести `fix_task` на нужную из заменяющих и поправить `tickets`. Записать это
     в `firm-plan.md` рядом с `superseded_by` и в промпт адъюдикации.

   Основание то же, что у остальной Д-12: решение человека должно иметь представление
   в данных, иначе оно существует только в голове того, кто его принял.

5. **`superseded_by` движок не читает** — и это отдельная строка правки, в `listTasks`
   (`lib/firm.mjs`): туда добавить `superseded_by: toArray(data.superseded_by)`. Сейчас
   функция читает одиннадцать полей шапки (`id`, `title`, `epic`, `status` как кэш,
   `depends_on`, `parallel_safe`, `ui`, `labels`, `br_refs`, `fixes`, `worktree`), и
   этого среди них нет.

   Важно не спутать это с чтением СТАТУСА из шапки: статус по ADR-0001 принадлежит
   журналу, и читать его из frontmatter нельзя — решение зажило бы в двух местах и
   начало расходиться. `superseded_by` — не статус, а ссылка на замену, и хранится она
   там же, где `depends_on` и `fixes`, по той же логике.

   Что это даёт проверке из пункта 4: `doctor` сможет не только назвать повисший баг, но
   и предложить кандидата. Одна задача в `superseded_by` — перевязка `fix_task`
   механическая; несколько (на прогоне 24.09.2026 было две, T-112 и T-113) — выбор за
   Архитектором, но движок покажет, из чего выбирать.

Проверять после правки: `sync` больше не трогает такие задачи, `build-args` их не выдаёт,
доска показывает терминальный статус, `doctor` ловит баги с повисшими ссылками.

### Д-13 — `post-merge` молчит, когда поставку слили на стороне GitHub — ЗАКРЫТ (0.4.10)

Хук вытаскивал имя влитой ветки из рефлога шаблоном `merge <ветка>:`. После `gh pr merge`
слияние происходит НЕ здесь: локально приезжает `git pull --ff-only`, и рефлог пишет
`pull --ff-only: Fast-forward`, где имени ветки нет вовсе. Шаблон не совпадал, и хук
молча не писал ничего — поставка слита, событий выпуска нет. На прогоне 24.09.2026 их
дописывали командой вручную.

**Закрыто:** когда рефлог имени не дал, хук берёт его из ПРИШЕДШИХ коммитов
(`ORIG_HEAD..HEAD`) — слияние PR оставляет `feature/<change>` в заголовке. Не нашли —
молчим: выдумать имя поставки хуже, чем не записать событие, потому что неправда в
журнале дороже дыры (дыру хотя бы видно в `doctor`).

### Д-14 — выпуск переписывал кэш статусов внутри архивного снимка — ЗАКРЫТ (0.4.10)

`tasksDir` намеренно ищет задачи в `openspec/changes/archive/`, если живого каталога уже

снимок иммутабелен (приём `firm-docs`, `skills/firm-docs/SKILL.md`), статус принадлежит журналу (ADR-0001), и кэш внутри

## Критерий, который описывает момент (разбор 05.10.2026, два проекта)

**Наблюдалось.** проект-В: тест `test_diff_against_delivery_branch_touches_only_files_in_scope`
из задачи T-039f с жёстко вписанным `ALLOWED_FILES` после слияния стал краснеть на диффе
ЛЮБОЙ следующей задачи и заблокировал приёмку очереди (BUG-047, снят задачей T-062). Это
четвёртый баг одного семейства — BUG-043, 045, 046 чинили формулировкой того же критерия, и
не помогло ни разу. Независимо, в другом проекте: проект-Б, BUG-018 —
`test_client_diff_has_no_hunk_outside_the_four_documented_pieces`, тест про собственный дифф
задачи, оказался вдобавок ложной гарантией (мутации двух ревьюеров прошли молча).

**Корень один, и он не в формулировках.** Роль судит о состоянии репозитория по снимку,
который к моменту предъявления устарел. Три его вида:

1. критерий со списком чужих красных («полный прогон зелёный, кроме этих трёх») — ложен
   после любого следующего слияния;
2. критерий про объём задачи, превращённый в ВЕЧНЫЙ тест в ветке поставки, — краснеет на
   всех следующих задачах;
3. `status` во frontmatter задачи, прочитанный как истина, — отстающий кэш (И-12: пока
   стадия держит рабочее дерево, движок в файл задачи не пишет). Замер того же дня: кэш
   отставал у 3 задач из 75, и T-058 стояла как `ready`, будучи влитой.

**Закрыто (0.4.59), четырьмя правками промптов:**

- во всех четырёх ролях, судящих о чужих задачах (Архитектор, Разработчик, Тестировщик,
  Ревьюер-QA) — раздел «Состояние ЧУЖОЙ задачи — только с доски»: `firm-state.mjs board
  --json`, и своей проверки «влито» не изобретать (ADR-0005);
- Тестировщик: критерий о собственном диффе, объёме или прогоне — доказательство стадии в
  `notes`, а не вечный тест. Правило: тест, который останется в ветке поставки, не имеет
  права знать номер своей задачи;
- Тестировщик и Ревьюер-QA: база прогона — merge-base, судится «нет НОВЫХ красных»;
  Ревьюер вдобавок обязан эскалировать непредъявимый критерий, а не отклонять по букве;
- Архитектор: критерий описывает поведение, а не состояние репозитория на день
  планирования.

**Побочно закрыто там же.** Промпты ролей ссылались на `$ENGINE/...` (памятка по линту —
с самого начала), а в оболочке субагента этой переменной нет: её задаёт команда в сессии
человека. Теперь сборщик кладёт путь в промпт стадии маркером `FIRM2-ENGINE`.

«команда не отработала» и не закрывает «отработала, а агент ответил `running`». Движок
спрашивал у модели факт, который умеет проверить сам.

**Закрыто:** паузу держит хук `SubagentStart` — код, а не субагент (ADR-0002). Новая
задача (старт `dev` без прежних событий `dev` по тикету) при стоящей паузе отклоняется
`exit 2` и отмечается событием `guard/pause-held`; доработка проходит, потому что пауза
значит «доработать начатое и не брать новых». Зонд в планировщике остался — он экономит
заведение рабочего дерева, — но единственной защитой быть перестал.

**K — стадия слияния уничтожает чужие правки.** Подтверждён дословно. Промпт советовал
`git stash push` на файл задачи, слияние, `sync`, затем `git stash drop` — в уверенности,
что там только кэш статуса. Файл задачи — рабочий документ Архитектора; так пропали его
правки примерно в десяти файлах. **Закрыто:** `pop` вместо `drop`, и сказано почему;
конфликт на `pop` — видимая работа человеку вместо тихой потери.

**L — запрет снимать песочницу жил только в тексте промпта.** Подтверждён: `PreToolUse`
стоял на `Write|Edit`, на `Bash` не стоял вовсе, и флаг `dangerouslyDisableSandbox` не
видел никто. Случай T-057 всплыл лишь потому, что Разработчик сам о нём написал.
**Закрыто:** хук `PreToolUse(Bash)` (`bash-guard.mjs`) отклоняет такой вызов из рабочего
дерева задачи; из главного дерева пропускает с предупреждением (там работает человек,
ADR-0009); ключ `guard.sandbox_off: allow` разрешает его проекту, но каждый вызов тогда
пишется событием `guard/sandbox-off`.

**M — `sync` отвечает двусмысленно.** Подтверждён. Строка `T-058: ready → merged (после
слияния)` читается как «уже применено»: стрелка выглядит сделанным действием. На этом
споткнулся Архитектор — прочитал у влитой T-058 `status: ready` и неверно определил объём
задачи. **Закрыто:** теперь сказано, что в файле СЕЙЧАС старое значение, а истина в
журнале. Само откладывание — не дефект, а И-12: пока стадия держит рабочее дерево, движок
в файл задачи не пишет.

**Не-дефект, с которым он прав.** Предупреждение о доле исключительных задач бесполезно,
когда цепочка последовательна по существу. Полезнее ожидаемая ширина прогона — отложено
до `plan-shape`.

### Д-15 — застрявшую стадию нечем заметить вовремя — ЗАКРЫТ (0.4.14)

Вопрос человека 24.09.2026: не ограничить ли стадию по времени, минут до 25. Разбор по
журналу Play (204 пары «старт-финиш» за поставку): медиана 3.9 минуты, 90-й процентиль
9.8, максимум 81.9; выше 25 минут — три стадии из 204, все `dev`. То есть порог отсекал бы
полтора процента работы.

**Жёсткий таймаут поставить нельзя.** `agent()` в Workflow принимает `label`, `phase`,
`schema`, `model`, `effort`, `isolation`, `agentType` — таймаута и отмены среди опций нет.
Обёртка с гонкой таймеров дела не меняет: выиграв гонку, скрипт не останавливает самого
агента, тот продолжает писать в рабочее дерево, а скрипт уже идёт дальше — получаются две
руки в одном дереве.

**И будь он возможен, ставить его не стоило бы.** Стадия, убитая на середине, оставляет
наполовину переписанный worktree без события финиша: тесты не запускались, вердикта нет,
а попытка уже потрачена. Цена при этом считается не минутами, а токенами — двадцать пять
минут Opus на честной задаче и столько же на петле стоят одинаково, и по часам их не
различить.

**Что сделано вместо.** Две половины, каждая по своей стороне границы:

1. **Снаружи — заметить.** `doctor` получил второй, мягкий порог: стадии, идущие дольше
   порога своей стадии (считается по журналу проекта, см. `stageThresholds`; до
   05.10.2026 порог был один на все стадии и равнялся 25 минутам), выходят списком `long_running` с
   номером задачи, стадией и возрастом. Считается по обоим спискам — привязанные стадии из
   `open_stages`, непривязанные из `pending_binding`, застревать они умеют одинаково. На
   `ok` не влияет: долгая стадия не поломка. С `abandoned_starts` (старше шести часов,
   финиша не будет вовсе) не пересекается — это разные сигналы и разные действия.
   Часовой монитор называет такие стадии в сводке.
2. **Изнутри — остановиться.** В промпт Разработчика добавлен `limitLine()`: один и тот же
   подход не сошёлся трижды — не заходить на четвёртый, вернуть `escalate: true` и описать
   в `notes`, что пробовал и какого решения не хватает. Предел задан признаком, а не
   часами, потому что агент надёжно видит свои попытки и ненадёжно — время. Эскалация
   здесь штатный ход маршрута: задача уходит в арбитраж (`firm-build.md` §3), решение принимает Архитектор
   или человек. Тестировщику того же не дано намеренно: в `TEST_SCHEMA` поля `escalate`
   нет, а добавлять его без обработки в цикле — заводить механизм, который никто не читает.
