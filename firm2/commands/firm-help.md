# /firm-help — справка по маршруту firm2

Выведи человеку эту справку (живо, по-русски, можно почти дословно):

## Что это

**firm2** — маршрут поставки фирмы-команды агентов. Он вырос из движка `agent-dev-firm`
(тот удалён в 0.3.0, роли переехали сюда) и отличается от него не ролями, а устройством
маршрута: он разрезан на **три сессии**, задачи живут **файлами**, а переходы между
стадиями пишет **код**, а не пересказ.

## Команды

| Команда | Что делает |
|---|---|
| **`/firm-setup`** | Настройка проекта: bootstrap, `.firm/config`, git-хук, линтер и тесты, границы песочницы, имена каталогов, граф кода. Один раз до разведки; повторный запуск безопасен и служит проверкой. |
| **`/firm-discovery`** | Разведка (груминг) одной темы **в своём рабочем дереве**: PM опрашивает человека, Архитектор отвечает «что менять в коде», Дизайнер перечисляет экраны → досье `docs/backlog/G-XXX-<слаг>/`, плюс `BRD-XXX`, ADR, словарь `CONTEXT.md`. Поставку не заводит (ADR-0012), идущей сборке не мешает, тем в разборе может быть сколько угодно разом. Про окружение здесь не спрашивают. |
| **`/firm-plan --from G-XXX`** | Планирование: вливает ветку груминга, заводит папку поставки, PM раскладывает досье в `proposal.md`, Архитектор режет задачи на файлы `T-XXX.md`, ведёт `design.md`, спеки-дельты и диаграммы; Дизайнер рисует UI-прототип. Финал — 🚪 ворота человека. |
| **`/firm-build`** | Сборка: параллельный цикл Dev→Test→QA до трёх задач сразу, слияние в `feature/<change>`, MR-ревью с `diff-impact`, 🚪 демо-ворота, мерж. |
| **`/firm-pause`** | Пауза сборки: начатое доводится до конца, новое не берётся. Аргументы: пусто — поставить, `resume` — снять, `status` — проверить. |
| **`/firm-adopt`** | Принять новую версию движка: вписать фактическую версию в `.firm/config` и показать заголовки CHANGELOG между старой и новой. Звать после обновления плагина, по разу в каждом проекте. Отметка, а не установка — новый код действует и без неё. |
| **`/firm-dashboard`** | Пересобрать и открыть дашборд: доска с зависимостями, тайминг, баги, последние события. |
| **`/firm-monitor`** | Пуш-сводки хода сборки раз в ~10 минут по журналу событий. Для случая «человек отошёл»; `/workflows` и дашборд не заменяет. |
| **`/firm-help`** | Эта справка. |

## Роли

Восемь: PM, Архитектор, Дизайнер, Разработчик, Тестировщик, Ревьюер-QA, Технический писатель,
DevOps — все с префиксом `firm2:` (`firm2:firm-architect` и так далее). Семь пришли из движка
`agent-dev-firm` вместе с восемью приёмами-скиллами; Дизайнер — своя.

## Чем маршрут держится

- **Задачи — файлы** `openspec/changes/<change>/tasks/T-XXX.md`. Доска только на чтение.
- **События переходов пишет код**: хуки рантайма на старте и завершении роли + git-хук
  `post-merge`. Один файл на событие — тогда параллельные ветки не конфликтуют при слиянии.
- **Статус в задаче — кэш.** При расхождении побеждает журнал событий.
- **Дашборд** (`.firm/dashboard.html`) пересобирается на каждом событии и не коммитится.
- **Тайминг показывает две метрики**: календарную и активную. Разница — ожидание,
  в первую очередь ожидание человека на воротах; это главный диагностический сигнал.

## Как начать

1. Один раз: `/plugin marketplace add <путь-к-marketplace>` → `/plugin install firm2@firm2 --scope user`.
2. В проекте: `/firm2:firm-setup` — поднять окружение и проверить настройки.
3. Затем `/firm2:firm-discovery "<задача>"` — разговор только про задачу. Движок заведёт
   тему `G-XXX` и своё дерево под неё; номер он назовёт в ответе.
4. Дальше `/firm2:firm-plan --from G-XXX`, потом `/firm2:firm-build`. Сборка — **по одной
   за раз**; груминг следующей темы при этом идти может, он в своём дереве.

Команды зови с префиксом `firm2:` — голое `/firm-help` двусмысленно, если в аккаунте
стоит ещё один плагин со своим `firm-help`.

## Где что лежит

| Документ | О чём |
|---|---|
| `docs/pilot-checklist.md` | порядок пилота, что проверять между сессиями, таблица «симптом → где искать» |
| `README.md` | состав плагина, как события попадают в журнал, таблица «роль → модель» |
| `docs/firm2-design.md` | замысел: 13 разделов решений и почему именно так |
| `docs/adr/` | три трудно-обратимых решения с обоснованием |

## Пауза и возобновление

```
/firm2:firm-pause           поставить паузу
/firm2:firm-pause resume    снять паузу
/firm2:firm-pause status    проверить, стоит ли
```

Пауза живёт файлом `.firm/current/pause.json`, а не состоянием сессии: её можно поставить
сегодня, а снять через неделю из другой сессии. Снимает её **человек** — движок сам не
снимает никогда: это решение, а не поломка, которую надо «починить».

После `resume` — обычный `/firm2:firm-build` в **новой** сессии. Уже влитые задачи он
заново не возьмёт: список строится из журнала, а `merged` из него исключены.

Полезные команды состояния (из проекта под firm2):

```bash
ENGINE="$(sed -nE 's/^engine_root:[[:space:]]*"?([^"#]+)"?[[:space:]]*$/\1/p' .firm/config)"
node "$ENGINE/scripts/firm-state.mjs" phase     # где мы и какая команда следующая
node "$ENGINE/scripts/firm-state.mjs" board     # доска задач
node "$ENGINE/scripts/firm-state.mjs" resume    # снять паузу, если команды не подтянулись
node "$ENGINE/scripts/firm-event.mjs" doctor    # дыры в журнале событий
node "$ENGINE/scripts/firm-event.mjs" abandon --ticket T-002   # закрыть стадию, брошенную снятым прогоном
node "$ENGINE/scripts/firm-event.mjs" record --ticket T-009 --stage merge --event finished \
  --corrects <файл-события>.json --notes "почему прежнее неверно"   # исправить ошибочное событие
node "$ENGINE/scripts/firm-state.mjs" prune    # снести осиротевшие и брошенные пустые worktree
node "$ENGINE/scripts/firm-state.mjs" adopt     # принять новую версию движка в .firm/config
```

Замеры — ничего не запрещают и ничего не закрывают, только считают:

```bash
node "$ENGINE/scripts/firm-state.mjs" mass       # масса репозитория: продукт против проверок
node "$ENGINE/scripts/test-audit.mjs"            # что в наборе тестов не окупается (приём firm-test-audit)
node "$ENGINE/scripts/context-bill.mjs"          # счёт контекста движка: чем он занимает окно до начала работы
```

У всех трёх код возврата ноль всегда. Находка замера — кандидат, а не приговор: решение
за человеком (ADR-0009).

`adopt` нужен после обновления плагина. Номер версии в `.firm/config` сам не меняется, и
это нарочно: он отвечает на вопрос «на какой версии проект вели», и автозапись стёрла бы
единственный признак того, что движок сменился под проектом, — раньше, чем человек его
увидит. Команда вписывает фактическую версию и показывает заголовки разделов CHANGELOG
между старой и новой, чтобы «стало 0.4.14» читалось как «приехало вот это».

Длинная форма через `node` нужна ровно в одном случае: команды не подтянулись в сессию —
плагин обновили, а сессию не перезапустили. Результат тот же. В остальных случаях зови
слэш-команду: она сама вычисляет `$ENGINE` и сама объясняет человеку, что происходит.

Присваивание `ENGINE=` и запуск — **одной строкой**: каждый вызов Bash идёт в своей
оболочке, и переменная между вызовами не живёт.

## Пока обкатывается

Маршрут меняет шесть механизмов сразу, поэтому первый прогон делается поэтапно и на
отдельном проекте.
